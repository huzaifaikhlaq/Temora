# Temora development data seeder

The seeder writes through four service-owned Django management commands. Identity creates users in the Identity database; Workspace creates workspaces and memberships in the Workspace database; Project creates projects in the Project database; Issue creates epics, issues, and child issues in the Issue database. The runner passes a JSON manifest between commands and never opens another service's database.

The issue service uses its existing `insert_issue` business logic for issue keys, project-scoped sequential numbering, epic references, and parent validation. Sprints, comments, and notifications are not seeded because those backend services/models are not implemented.

## Enable local seeding

From the repository root in Windows PowerShell, explicitly enable the development guard and start the services:

```powershell
$env:TEMORA_ENVIRONMENT = "development"
$env:TEMORA_SEEDING_ENABLED = "true"
docker compose up -d --build identity workspace project issue
```

The Compose services must have their normal local `.env` files configured. Apply migrations to each service database once:

```powershell
docker compose exec identity python manage.py migrate
docker compose exec workspace python manage.py migrate
docker compose exec project python manage.py migrate
docker compose exec issue python manage.py migrate
```

## Generate demo data

Dry run reports the planned counts without creating records:

```powershell
.\scripts\seed_demo.ps1 -Size medium -Seed 41 -DryRun
```

Seed one of the supported sizes:

```powershell
.\scripts\seed_demo.ps1 -Size small -Seed 41
.\scripts\seed_demo.ps1 -Size medium -Seed 41
.\scripts\seed_demo.ps1 -Size large -Seed 41
```

To make these workspaces visible to your existing local account, retrieve its UUID and pass it as an additional member. This adds that account to all three seeded workspaces:

```powershell
docker compose exec identity python manage.py shell -c "from accounts.models import User; print(list(User.objects.filter(full_name__icontains='your name').values_list('id', flat=True)))"
.\scripts\seed_demo.ps1 -Size medium -Seed 41 -AdditionalMemberId "<your-user-uuid>"
```

Sizes mean 100, 1,000, or 10,000 base issues. The base count includes epics (6%); child issues are additional at 15% of the base count. Every size creates 20 users, 3 workspaces, 36 memberships, and 12 projects. Passing `-AdditionalMemberId` adds one membership per workspace. Data includes issue descriptions, realistic engineering titles, statuses, priorities, tags, components, story points, due dates, epic links, parent links, and workspace-member assignments. Credentials use random passwords that are never printed; the generated accounts use the reserved `demo.temora.invalid` domain.

The same seed can be run again safely. Users, workspaces, projects, and issues use stable seed-specific identifiers/markers and existing marked records are reused. Increasing the size adds the missing records. A smaller size does not remove records generated by an earlier larger run.

## Remove only generated data

With the same explicit environment flags, remove the seed's generated records in dependency order:

```powershell
.\scripts\seed_demo.ps1 -Seed 41 -Cleanup
```

Preview cleanup counts first:

```powershell
.\scripts\seed_demo.ps1 -Seed 41 -Cleanup -DryRun
```

If you seeded with `-AdditionalMemberId`, pass the same ID to cleanup so the seeder can recognize that membership as generated:

```powershell
.\scripts\seed_demo.ps1 -Seed 41 -Cleanup -AdditionalMemberId "<your-user-uuid>"
```

Cleanup removes only issues tagged `td:41`, projects whose descriptions start with `[temora-demo-seed:41]`, workspaces whose names start with `Temora Demo [seed:41]`, and users whose reserved email starts with `temora-demo-41-`. It does not drop schemas, reset Docker volumes, or delete unmarked records. If an unmarked issue still references a generated project, that project and its workspace are retained. A workspace with memberships outside the generated user set or with a changed membership count is retained, and users still referenced by any workspace membership are retained. The issue service removes generated child issues before generated parents, unlinks generated epic references first, and removes counters only when no issue remains in that project.

## Run tests

```powershell
docker compose exec identity python manage.py test accounts
docker compose exec identity python manage.py test accounts.test_seeder
docker compose exec workspace python manage.py test workspaces
docker compose exec workspace python manage.py test workspaces.test_seeder
docker compose exec project python manage.py test projects
docker compose exec project python manage.py test projects.test_seeder
docker compose exec issue python manage.py test issues
docker compose exec issue python manage.py test issues.test_seeder
```

The service tests cover membership ownership and isolation, project workspace scoping, deterministic repeat behavior, issue numbering and parent/epic relationships, cross-project epic rejection, generated-only cleanup, and the development safety gate.

## Inspect the seeded data

Use the service-owned models from Django shell. For example, count generated records in each service:

```powershell
docker compose exec identity python manage.py shell -c "from accounts.models import User; print(User.objects.filter(email__startswith='temora-demo-41-').count())"
docker compose exec workspace python manage.py shell -c "from workspaces.models import Workspace, Membership; print(Workspace.objects.filter(name__startswith='Temora Demo [seed:41]').count(), Membership.objects.filter(workspace__name__startswith='Temora Demo [seed:41]').count())"
docker compose exec project python manage.py shell -c "from projects.models import Project; print(Project.objects.filter(description__startswith='[temora-demo-seed:41]').count())"
docker compose exec issue python manage.py shell -c "from issues.models import Issue; print(Issue.objects.filter(tags__contains=['td:41']).count())"
```

The generated records are available through the existing workspace, project, and issue API routes when accessed with a valid workspace member session. The seeder creates each account with a unique random password and never prints or persists that password in its manifest. Set a local password through your own development identity workflow if you need to sign in as a generated account.
